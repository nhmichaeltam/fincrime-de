# FinCrime DE

An end-to-end financial crime analytics data pipeline built on a modern, production-aligned data engineering stack. Designed to demonstrate real-world analytics engineering capabilities in the financial crime and fraud detection domain.

---

## What This Project Does

FinCrime DE simulates the core data infrastructure of a financial crime intelligence team at a UK payments company. It ingests 24 million synthetic credit card transactions alongside customer and card reference data, transforms them into a clean analytical model, runs on an automated daily schedule via Airflow, and surfaces fraud and risk analytics through a tested, documented, version-controlled pipeline.

The pipeline covers the full data engineering lifecycle:

- **Ingest** — three source datasets land in Google Cloud Storage as the raw immutable zone
- **Load** — an Airflow-orchestrated Python pipeline loads data into BigQuery, with distinct ingestion patterns for reference data, historical bootstrap, and ongoing daily incremental loads
- **Transform** — dbt models clean, type-cast, join, and aggregate across staging, intermediate, and mart layers
- **Test** — dbt generic tests enforce data quality at every layer (not_null, unique, referential integrity)
- **Orchestrate** — Apache Airflow schedules daily transaction ingestion and downstream dbt runs, with backfill demonstrated across the 2019–2020 window
- **Serve** — a Looker Studio dashboard built directly on the mart layer surfaces fraud rate trends, transaction growth, and customer risk scores

---

## The Business Scenario

The pipeline simulates the work of an analytics engineer embedded in a financial crime team. The business need: raw transaction data arrives daily from upstream card processing systems, and the fraud and compliance teams need a reliable, refreshable, analytically-ready layer — not raw logs they have to interpret themselves.

The models, tests, and aggregates exist to answer questions a real fraud operations or AML team would ask:

- Which customers have the highest composite risk scores, combining fraud history, error rates, and creditworthiness signals?
- How does the daily fraud rate trend over time, and where are the anomalous spikes worth investigating?
- Which cards are flagged as compromised on the dark web, and how does that correlate with transaction fraud rates?
- What is the total value of fraudulent transactions each day, and how does the fraud amount rate compare to the transaction count rate?

## Dataset

**Source:** IBM Credit Card Transactions (Kaggle: `ealtman2019/credit-card-transactions`)

A synthetic dataset generated by IBM Research simulating realistic consumer credit card spending behaviour across 2,000 customers holding multiple cards each, spanning 30 years of transaction history (1991–2020), approximately 24 million transactions totalling 2.35GB.

The dataset is genuinely relational across three files:

| File | Rows | Role in pipeline |
|---|---|---|
| `sd254_users.csv` | 2,000 | Customer demographics, FICO score, income, location |
| `sd254_cards.csv` | 6,146 | Card brand, type, credit limit, dark web flag |
| `credit_card_transactions-ibm_v2.csv` | ~24M | Every transaction event |

A fourth file (`User0_credit_card_transactions.csv`) was reviewed and deliberately excluded — it is a single-user demo subset provided by the publisher, redundant with the main transactions file.

The three-table structure mirrors the `customer → card → transaction` hierarchy used in real banking data warehouses, enabling meaningful dimensional joins across customer demographics, card attributes, and transaction behaviour — questions that cannot be answered from a flat transaction log alone.

## Ingestion Strategy

The ingestion design uses three distinct patterns to reflect how different types of data are handled in a real production pipeline:

### Reference Data (one-time load)
Customer and card data is loaded once in full via the `fincrime_reference_load` Airflow DAG. In production, this data would be managed by a core banking or card management system and refreshed on a slow cadence — treating it as a one-time dimension load reflects this genuine architectural separation.

### Historical Bootstrap Load (1991–2018)
Approximately 20 million transaction rows covering 1991 to 2018 are loaded in a single bootstrap operation. This is a standard, named production pattern: when a new pipeline is launched against a pre-existing data source, the historical baseline is bulk-loaded in one run before the scheduler takes over for ongoing incremental processing. Replaying decades of history through a daily job one row at a time would be both impractical and architecturally incorrect.

### Daily Incremental Ingestion (2019–2020)
Transactions from 2019 onwards are processed by the `fincrime_daily_transactions` Airflow DAG running `@daily`. Each run uses Airflow's `{{ ds }}` execution-date templating to load only that day's transactions, appending them to the raw transactions table. A backfill across the 2019–2020 window demonstrates Airflow's native catchup capability — a standard production requirement when a pipeline is first deployed against existing data.

### Why this approach, and why it is honest

The IBM dataset is synthetic and static — it does not generate new records daily the way a live card network would. Rather than obscuring this or engineering an artificial workaround, the pipeline makes the simulation explicit and names the real engineering patterns it is demonstrating:

- The bootstrap/incremental separation is a real production pattern, not a portfolio convention
- The `{{ ds }}` date templating is identical to what production pipelines use against genuinely live sources
- Airflow's catchup functionality is the same mechanism used when real pipelines are deployed against pre-existing data

In a production environment, this pipeline would be pointed at a real-time card processing feed — the patterns, decisions, and orchestration logic would be unchanged.

## Data Model

The mart layer uses a **denormalised wide fact table** design: customer and card attributes are joined into `fact_transactions` at the intermediate layer, rather than maintained as separate dimension tables. This prioritises query simplicity and BI tool performance — a single table scan covers all analytical questions without multi-hop joins.

```
stg_users ────┐
stg_cards ────┼──► int_transactions_enriched ──► fact_transactions
stg_txns  ────┘                                ──► daily_fraud_rate
                                               ──► customer_risk_score
```

**Mart models:**

| Model | Grain | Purpose |
|---|---|---|
| `fact_transactions` | One row per transaction | Wide denormalised fact table — every transaction with user and card attributes joined in |
| `daily_fraud_rate` | One row per calendar day | Daily transaction count, fraud count, fraud rate %, and flagged amount — primary dashboard data source |
| `customer_risk_score` | One row per customer | Composite risk score: `(fraud_rate_pct × 0.5) + (error_rate_pct × 0.2) + FICO band penalty` |

## Data Quality

Data quality is enforced at every model layer via dbt generic tests defined in `schema.yml`:

- **not_null** on all key columns (user_id, transaction_date, amount, is_fraud)
- **unique** on primary keys (user_id in stg_users, transaction_day in daily_fraud_rate, user_id in customer_risk_score)
- **referential integrity** via foreign key relationship tests between staging models

18 tests pass on every dbt run. Tests execute as the final step of each Airflow DAG run — a failed test blocks the pipeline from silently serving bad data downstream.

## Known Limitations and Future Work

- **Static source data:** the IBM dataset is synthetic and does not generate new records. In production, the pipeline would be pointed at a real-time card processing feed. The orchestration patterns (scheduling, backfill, incremental loading) are identical regardless of source.
- **Dimension tables:** the current design uses a denormalised wide fact table rather than a Kimball-style star schema with separate `dim_customer` and `dim_card` tables. A full SCD Type 2 approach on customer risk attributes would be appropriate for a production AML system where historical profile snapshots are needed for investigation audit trails.
- **Rule-based fraud flagging:** the current risk scoring uses deterministic rule-based logic. A natural extension would be an ML scoring layer (e.g. a gradient boosting model served via Vertex AI) replacing or augmenting the rules.
- **Idempotency on incremental loads:** the current incremental ingestion script appends rows on each run. A deduplication step in the staging dbt model or a pre-delete pattern in the ingestion script would be added before this pipeline was production-ready.
- **CI/CD:** a GitHub Actions workflow for linting and dbt tests on pull requests is the logical next addition to the project.
