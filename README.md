# FinCrime DE
 
An end-to-end financial crime analytics data pipeline built on a modern, production-aligned data engineering stack. Designed to demonstrate real-world analytics engineering capabilities in the financial crime and fraud detection domain.
 
---
 
## What This Project Does
 
FinCrime DE simulates the core data infrastructure of a financial crime intelligence team at a UK payments company. It ingests 24 million synthetic credit card transactions alongside customer and card reference data, transforms them into a clean dimensional model, runs on an automated daily schedule via Airflow, and surfaces fraud and risk analytics through a tested, documented, version-controlled pipeline.
 
The pipeline covers the full data engineering lifecycle:
 
- **Ingest** — three source datasets land in Google Cloud Storage as the raw immutable zone
- **Load** — an Airflow-orchestrated Python pipeline loads data into BigQuery, with distinct ingestion patterns for reference data, historical bootstrap, and ongoing daily incremental loads
- **Transform** — dbt models clean, type-cast, join, and aggregate across staging, intermediate, and mart layers
- **Test** — dbt generic and custom tests enforce data quality at every layer
- **Orchestrate** — Apache Airflow schedules daily transaction ingestion and downstream dbt runs, with backfill demonstrated across the 2019–2020 window
- **Serve** — a Looker Studio dashboard built directly on the mart layer surfaces fraud rate trends, customer risk scoring, and AML-relevant transaction patterns
---
 
## The Business Scenario
 
The pipeline simulates the work of an analytics engineer embedded in a financial crime team. The business need: raw transaction data arrives daily from upstream card processing systems, and the fraud and compliance teams need a reliable, refreshable, analytically-ready layer — not raw logs they have to interpret themselves.
 
Every model, test, and aggregate in this project exists to answer a question a real fraud operations or AML team would ask:
 
- Are transactions on cards flagged as compromised on the dark web more likely to be fraudulent?
- Do customers with lower FICO scores show higher fraud rates across transaction types?
- Which customers show velocity patterns — multiple transactions in a short window — that are consistent with account takeover or structuring behaviour?
- How does the daily fraud rate trend over time, and are there anomalous spikes worth investigating?

## Dataset
 
**Source:** IBM Credit Card Transactions (Kaggle: `ealtman2019/credit-card-transactions`)
 
A synthetic dataset generated by IBM Research simulating realistic consumer credit card spending behaviour across 2,000 customers holding multiple cards each, spanning 30 years of transaction history (1991–2020), approximately 24 million transactions totalling 2.35GB.
 
The dataset is genuinely relational across three files:
 
| File | Rows | Role in pipeline |
|---|---|---|
| `sd254_users.csv` | 2,000 | `dim_customer` — demographics, FICO score, income, location |
| `sd254_cards.csv` | 6,146 | `dim_card` — card brand, type, credit limit, dark web flag |
| `credit_card_transactions-ibm_v2.csv` | ~24M | `fct_transactions` — every transaction event |
 
A fourth file (`User0_credit_card_transactions.csv`) was reviewed and deliberately excluded — it is a single-user demo subset provided by the publisher, redundant with the main transactions file.
 
The three-table structure mirrors the `customer → card → transaction` hierarchy used in real banking data warehouses, enabling meaningful dimensional joins: transaction volume and fraud rates can be segmented by customer demographic, card type, credit limit, and compromise status — questions that cannot be answered from a flat transaction log alone.

## Ingestion Strategy
 
The ingestion design deliberately uses three distinct patterns to reflect how different types of data are handled in a real production pipeline:
 
### Reference Data (one-time load)
Customer and card data is loaded once in full. In production, this data would be managed by a core banking or card management system and refreshed on a slow cadence — it is not part of the daily transaction processing job. Treating it as a one-time dimension load reflects this genuine architectural separation.
 
### Historical Bootstrap Load (1991–2018)
Approximately 20 million transaction rows covering 1991 to 2018 are loaded in a single bootstrap operation. This is a standard, named production pattern: when a new pipeline is launched against a pre-existing data source, the historical baseline is bulk-loaded in one run before the scheduler takes over for ongoing incremental processing. Replaying decades of history through a daily job one row at a time would be both impractical and architecturally incorrect.
 
### Daily Incremental Ingestion (2019–2020)
Transactions from 2019 onwards are processed by a scheduled Airflow DAG running `@daily`. Each run uses Airflow's `{{ ds }}` execution-date templating to load only that day's transactions, appending them to the raw transactions table. A backfill run across the full 2019–2020 window demonstrates Airflow's native backfill capability — a standard production requirement when a pipeline is first deployed against existing data.
 
### Why this approach, and why it is honest
 
The IBM dataset is synthetic and static — it does not generate new records daily the way a live card network would. Rather than obscuring this or engineering an artificial workaround (splitting the file into thousands of tiny daily objects in GCS, or switching to a live but domain-irrelevant source), the pipeline makes the simulation explicit and names the real engineering patterns it is demonstrating:
 
- The bootstrap/incremental separation is a real production pattern, not a portfolio convention
- The `{{ ds }}` date templating is identical to what production pipelines use against genuinely live sources
- Airflow's backfill functionality is the same mechanism used when real pipelines are first deployed against pre-existing data
In a production environment, this pipeline would be pointed at a real-time card processing feed — the patterns, decisions, and orchestration logic would be unchanged. The dataset is the simulator; the engineering is real.

## Data Model
 
The mart layer follows a Kimball-style star schema, with `fct_transactions` as the central fact table and two conformed dimension tables that can be reused across any downstream analytical model.
 
```
dim_customer ──┐
               ├──► fct_transactions
dim_card ──────┘
```
 
**Fact table grain:** one row per transaction. The grain is enforced by a `unique` dbt test on `transaction_id`.
 
**Key modelling decisions:**
 
- **Surrogate keys** are generated via `dbt_utils.generate_surrogate_key` rather than relying on raw integer IDs from the source — this is stable even if the upstream key logic changes
- **SCD Type 2 snapshot** on `dim_customer` risk attributes (FICO score, income band) preserves history — important for AML investigations that need to know a customer's risk profile *at the time of a transaction*, not just today
- **Star schema over snowflake** — dimensions join directly to the fact table in one hop, prioritising query simplicity and BI tool performance over storage normalisation
- **Partitioning and clustering** on `fct_transactions` — partitioned by `transaction_date`, clustered by `transaction_type` — to enable partition pruning on daily queries and reduce BigQuery scanning costs
**Aggregate mart models** built on top of the star schema:
 
| Model | Purpose |
|---|---|
| `agg_daily_fraud_rate` | Daily transaction count, fraud count, fraud rate %, and total flagged amount — primary dashboard data source |
| `agg_customer_risk_score` | Composite per-customer risk score combining FICO score, transaction velocity, CASH-OUT proportion, structuring indicators, and dark-web card exposure |
| `agg_velocity_alerts` | Customers with transaction counts exceeding a configurable threshold within a rolling window — a real AML detection heuristic |

## Data Quality
 
Data quality is enforced at multiple layers:
 
- **dbt generic tests** on every model: `not_null`, `unique`, `accepted_values`, `relationships` (referential integrity between fact and dimension tables)
- **dbt_expectations tests** for range validation: amount always greater than zero, fraud rate never exceeds a configurable threshold
- **Custom singular tests** for domain-specific logic: no transaction can have a negative amount; every transaction in `fct_transactions` must resolve to a valid customer in `dim_customer`
- **Source freshness checks** configured in `sources.yml` — dbt warns if the raw data has not been refreshed within the expected window

## Known Limitations and Future Work
 
- **Static source data:** the IBM dataset is synthetic and does not generate new records. In production, the pipeline would be pointed at a real-time card processing feed or settlement file system. The orchestration patterns (scheduling, backfill, incremental loading) are identical regardless of source.
- **Rule-based fraud flagging:** the current risk scoring uses deterministic rule-based logic. A natural extension would be an ML scoring layer (e.g. a logistic regression or gradient boosting model served via Vertex AI) replacing or augmenting the rules.
- **Streaming extension:** a separate future project will demonstrate a streaming ingestion pattern (Kafka / Pub-Sub) to complement this batch pipeline, using a live financial data API as the source.
- **Idempotency on incremental loads:** the current incremental ingestion script appends rows on each run. A deduplication step in the staging dbt model or a pre-delete pattern in the ingestion script would be added before this pipeline was production-ready.
